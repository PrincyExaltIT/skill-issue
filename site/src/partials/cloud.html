@@ cloud · C.2 @@GitHub Actionscore20 min

Atelier · ta review sur chaque PR GitHub

Le workflow a deux jobs. Le premier tourne pour tout le monde, sans IA ni secret ; le second lance le skill complet avec l'agent de ton équipe, Claude Code ou Codex, dès que sa clé est configurée.

Extrait de course/ci/github/revue-angular.yml ↗, raccourci pour la page. Le fichier complet est dans le dépôt du kit : c'est lui que tu copies dans l'atelier.

# extrait de course/ci/github/revue-angular.yml
on:
  pull_request:

jobs:
  verifs:                       # sans IA : la porte
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0        # le périmètre a besoin de l'ancêtre commun
      - uses: actions/setup-node@v7
        with:
          node-version: 24
      - run: diff -r .agents/skills/revue-angular .claude/skills/revue-angular
      - run: |
          node .agents/skills/revue-angular/scripts/perimetre.mjs --base origin/${{ github.base_ref }}
          node .agents/skills/revue-angular/scripts/verifs.mjs --echec-sur BLOCKER

  revue-ia-claude:              # avec IA : le skill complet, par Claude Code
    needs: verifs
    if: ${{ !cancelled() }}     # aussi quand la porte est fermée : c'est là qu'elle sert
    permissions: { contents: read, pull-requests: write, id-token: write }
    env:
      HAS_KEY: ${{ secrets.ANTHROPIC_API_KEY != '' }}
    steps:
      # sans clé : un simple message. Avec clé, chaque étape suivante porte
      # « if: env.HAS_KEY == 'true' » (le fichier complet les écrit toutes).
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: /revue-angular Relis cette PR (base : origin/${{ github.base_ref }}).
          claude_args: --allowedTools "Bash(git:*),Bash(node:*),Read,Grep,Glob,Write"
      - run: gh pr comment ${{ github.event.pull_request.number }} --body-file .review/REVIEW.md
        env: { GH_TOKEN: ${{ github.token }} }

  revue-ia-codex:               # le même skill, par Codex (secret OPENAI_API_KEY)
    # … mêmes needs, if, checkout et publication ; seule l'étape de l'agent change :
      - uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          permission-profile: ':workspace'
          prompt: $revue-angular Relis cette PR (base : origin/${{ github.base_ref }}).
  • Le skill par son nom, quel que soit l'agent. actions/checkout d'abord, puis le nom du skill dans le prompt : /revue-angular pour Claude Code, qui le lit dans .claude/skills/, $revue-angular pour Codex, qui le lit dans .agents/skills/. Les deux jobs partent du même dossier de skill, produisent le même rapport et le publient par la même étape, alors garde celui de ton équipe et supprime l'autre.
  • Le script pose les annotations, l'IA écrit le commentaire. En GitHub Actions, verifs.mjs écrit chaque piste en annotation sur le diff (une ligne ::error ou ::warning), sans rien changer à la commande.
  • L'agent écrit le rapport, le workflow publie le commentaire. L'agent écrit .review/REVIEW.md ; une étape ordinaire le publie avec le token du workflow. La liste --allowedTools ne lui donne ni gh ni outil de commentaire.
  • id-token: write (job Claude Code) : sans github_token, l'action s'authentifie auprès de GitHub comme l'app GitHub de Claude. Avec ce token d'app, elle peut lire et écrire le contenu du dépôt, les issues et les pull requests (les droits qu'elle demande ; l'app officielle en demande davantage). L'agent n'est donc pas « sans accès » à GitHub. Pour la cantonner, passe ton propre github_token (celui du workflow, ou une app limitée à ces droits).

Atelier cloud · ta PR relue en CI

Il te faut : les deux dépôts de l'atelier 0 côte à côte (skill-issue-playground et skill-issue), un skill avec ses scripts (atelier 3 au moins ; sinon le skill de référence, voir le rattrapage), et un compte GitHub. Compte 20 minutes.

  1. Fork avec toutes les branches. Sur la page de PrincyExaltIT/skill-issue-playground, clique sur Fork. Le formulaire propose « Copy the … branch only » (le nom de la branche par défaut, ici depart), cochée par défaut : décoche-la. Sinon ton fork n'a ni lab/speaker-spotlight ni equipe/…, et il n'y a rien à relire.
  2. Active les workflows. GitHub les désactive sur les forks : onglet Actions de ton fork, puis « I understand my workflows, go ahead and enable them ».
  3. Clone ton fork dans un dossier à part, place-toi sur la PR du lab et crée ta branche : elle portera le lab, ton skill et le workflow. 
    $ git clone https://github.com/<ton-compte>/skill-issue-playground.git mon-fork
$ cd mon-fork
$ git checkout lab/speaker-spotlight   # la PR du lab
$ git checkout -b ma-revue
  4. Ajoute ton skill, dans les deux dossiers, et le workflow, puis pousse. 
    $ mkdir -p .claude/skills .agents/skills .github/workflows
$ cp -r ../skill-issue-playground/.claude/skills/revue-angular .claude/skills/   # ton skill (.agents/skills/ si tu es sous Codex)
$ cp -r .claude/skills/revue-angular .agents/skills/
$ cp ../skill-issue/course/ci/github/revue-angular.yml .github/workflows/
$ git add .claude .agents .github && git commit -m "ci: la revue-angular de l'équipe"
$ git push -u origin ma-revue
  5. Ouvre la PR sur ton fork, vers depart. Par défaut, GitHub vise le dépôt d'origine : change-le. 
    $ gh pr create --repo <ton-compte>/skill-issue-playground --base depart --head ma-revue --fill
    Sur le site, c'est « Compare & pull request », puis « base repository » = ton fork, base = depart, compare = ma-revue.
  6. Regarde la porte se fermer (onglet Checks de la PR) et les annotations arriver sur le diff (onglet Files changed). Puis, si ton équipe a une clé : ajoute le secret ANTHROPIC_API_KEY (Settings, Secrets and variables, Actions) et installe l'app GitHub de Claude sur ton fork (/install-github-app dans Claude Code, droits admin requis), ou le secret OPENAI_API_KEY pour Codex ; puis relance le job « Revue IA » correspondant. Sans clé, la porte suffit à l'atelier. Cette dernière étape, nous ne l'avons pas testée : si elle échoue, le journal du job te le dit.

Pourquoi une branche qui contient le lab ? Les scripts excluent .claude/ et .agents/ du périmètre. Une PR qui ne contient que le skill et le workflow a donc un périmètre vide : la porte reste verte et tu ne vois rien se fermer.

Aucun run ne démarre ? Sur le dépôt de démo, les premières PR n'ont déclenché aucun run tant qu'aucun workflow n'avait tourné sur un push (voir C.6). Ferme et rouvre la PR. Si rien ne bouge, pousse un commit vide : git commit --allow-empty -m relance && git push.

Tu as forké sans décocher la case ? Rapatrie les deux branches depuis le dépôt d'origine, dans ton clone du fork : git remote add upstream https://github.com/PrincyExaltIT/skill-issue-playground.git && git fetch upstream && git push origin upstream/lab/speaker-spotlight:refs/heads/lab/speaker-spotlight upstream/equipe/speaker-spotlight:refs/heads/equipe/speaker-spotlight

Fini quand : la porte est rouge sur ta PR (avec le skill de référence : SEC-01, SIG-01 et A11Y-02 ; avec le tien, tes règles BLOCKER), les annotations sont sur le diff, et, si tu as mis une clé, le commentaire de la revue IA cite des fichier:ligne que tu retrouves dans ton rapport local (.review/REVIEW.md).

Rattrapage : ton skill n'est pas prêt ? Dans mon-fork, node ../skill-issue/course/rattrapage.mjs 5 --harness tous met le skill de référence dans les deux dossiers (ton clone skill-issue-playground n'est pas touché). Ou, après le clone (étape 3), prends la branche toute faite : git checkout equipe/speaker-spotlight porte le lab, le skill de référence et le workflow, et elle est déjà dans ton fork. Ouvre alors la PR (étape 5) avec --head equipe/speaker-spotlight.

@@ cloud · C.3 @@GitLab CIcore7 min

La même chose sur GitLab

Le skill et ses scripts ne bougent pas ; côté GitLab, ce sont deux jobs dans .gitlab-ci.yml. L'intégration de Claude Code dans GitLab CI/CD est en bêta et maintenue par GitLab. Le job sans IA a tourné pour de vrai le 9 octobre 2026 sur gitlab.com : la MR !1 du dépôt de démo a calculé son périmètre (15 fichiers), trouvé 3 pistes BLOCKER et fermé la porte en 24 secondes, comme sur GitHub. Le job IA, lui, n'a jamais tourné : il faut une clé, et le dépôt de démo n'en a pas.

Un compte gitlab.com tout neuf doit d'abord vérifier son identité (par téléphone ; GitLab peut aussi demander une carte) : sans ça, chaque pipeline échoue avant le premier job, avec « the user not being verified ».

variables:

  rules: [{ if: $CI_PIPELINE_SOURCE == "merge_request_event" }]

    - node .agents/skills/revue-angular/scripts/verifs.mjs --echec-sur BLOCKER

revue-angular:ia:
  rules: [{ if: $CI_PIPELINE_SOURCE == "merge_request_event" && $ANTHROPIC_API_KEY && $GITLAB_REVIEW_TOKEN }]
  script:
    - npm install -g @anthropic-ai/claude-code
    - claude -p "/revue-angular Relis cette MR (base : origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME)." --permission-mode acceptEdits --allowedTools …

  • Variables masquées : ANTHROPIC_API_KEY, et un token de projet de scope api pour écrire la note (ici GITLAB_REVIEW_TOKEN).
  • Déclencher par un commentaire : la doc de Claude Code pour GitLab décrit aussi un webhook qui lance le pipeline quand un commentaire de MR contient @claude.
  • Le gabarit complet est dans course/ci/gitlab/revue-angular.gitlab-ci.yml ; il est commité sur la branche equipe/main du dépôt de démo, recopié sur gitlab.com/PrincyExaltIT/skill-issue-playground. Pour recopier ton propre dépôt : glab auth login, puis bash kit/gitlab-mirror.sh <groupe>.

Agents et sessions cloud

Dernière marche, l'agent complet. Il tourne sur une machine distante, clone ton dépôt et y trouve ton skill.

  • Claude Code on the web : des sessions Claude Code sur l'infrastructure d'Anthropic, lancées depuis claude.ai/code, l'app desktop ou claude --cloud. Elles clonent le dépôt GitHub et chargent les skills de son .claude/skills/ ; tes skills personnels restent sur ta machine. GitLab et Bitbucket ne sont pas clonés.
  • Les routines : un prompt, des dépôts et des déclencheurs (planning, appel d'API, événement GitHub comme l'ouverture d'une PR), exécutés dans le cloud. Une routine « à chaque PR, lance /revue-angular » joue le rôle de ta CI, sans fichier de CI. Attention : les connecteurs branchés sont inclus par défaut, et leurs outils d'écriture tournent sans demande de permission. Retire ceux dont la review n'a pas besoin.
  • /code-review ultra : une flotte d'agents dans le cloud, qui reproduit chaque finding avant de le publier (5 à 10 minutes). claude ultrareview --json le lance depuis une CI. Ton skill n'y tourne pas, alors prends son résultat comme un deuxième avis, à comparer au tien.
  • Codex cloud et les Dots d'OpenAI : les tâches Codex tournent aussi dans des environnements distants. D'après la presse (TechCrunch, 29 septembre 2026), OpenAI aurait présenté à son DevDay des « Dots », des agents qui tournent en continu. Un récapitulatif du DevDay existe sur openai.com, mais nous n'avons pas pu le lire, et rien ne décrit leur usage pour la review de code.
@@ cloud · C.6 @@pitfalls · costscore7 min

Pièges, sécurité et coûts

  • Forks : GitHub ne transmet pas les secrets aux workflows lancés par une PR de fork. Ta porte sans IA tourne quand même ; la revue IA, non. Sur un dépôt public, c'est le comportement attendu.
  • Bots : l'action Claude refuse les PR ouvertes par un bot (Dependabot, Renovate) sauf s'il figure dans allowed_bots.
  • pull_request_target : ne l'utilise pas pour lancer un agent sur le code d'une PR. Il donne des droits d'écriture et des secrets à un code non relu.
  • Annotations : sur nos runs, GitHub n'a affiché que dix annotations par niveau et par étape, ce que confirme la documentation de l'API Checks (10 avertissements et 10 erreurs par étape pour GitHub Actions). Trie tes pistes par gravité, et publie la liste complète ailleurs (résumé du job ou commentaire).
  • Dépôt neuf : sur le dépôt de démo, les premières PR n'ont déclenché aucun run tant qu'aucun workflow n'avait tourné sur un push. Fermer et rouvrir la PR a ensuite suffi. Nous l'avons constaté nous-mêmes ; GitHub ne documente pas ce comportement.
  • Données : un relecteur hébergé envoie ton code à son fournisseur. Vérifie que c'est permis pour ce dépôt avant de l'activer.
