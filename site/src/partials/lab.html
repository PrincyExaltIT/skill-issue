Ta première review en 30 minutes

Une vraie branche Angular 22, écrite trop vite, avec {{LAB_ISSUES}} problèmes cachés. Tu lances le skill, tu lis le rapport, tu mesures ce qu'il a trouvé, tu corriges, tu passes le relais.

⏱ 30 min8 étapes · 3 bonusdépôt : skill-issue-playground

Récupérer les deux dépôts

Le kit (les skills, l'installeur, les evals) et l'application de démo « Conf Planner » (Angular 22.2, zoneless, Vitest).

$ git clone https://github.com/PrincyExaltIT/skill-issue.git
$ git clone https://github.com/PrincyExaltIT/skill-issue-playground.git
$ cd skill-issue-playground && npm ci

Node.js 24.15 ou plus récent est requis par Angular 22 (node --version).

Voir ce que l'équipe a installé

Les skills sont versionnés dans le dépôt, comme le ferait une équipe : .agents/skills/ (Codex, Copilot, Cursor, Gemini CLI, OpenCode…) et .claude/skills/ (Claude Code). Si ton harness lit un autre dossier, l'installeur s'en charge :

$ ls .agents/skills
angular-review  pr-handoff  review-fix  skill-smith
$ node ../skill-issue/kit/install.mjs --list
$ node ../skill-issue/kit/install.mjs --target . --harness kilo

Passer sur la branche à relire

$ git checkout feat/speaker-spotlight
$ git log --oneline main..HEAD
$ npm run build
Le build passe. Les bugs sont ailleurs : à l'exécution (NG0203), dans la vue qui ne se rafraîchit pas (zoneless), dans la sécurité, l'accessibilité et les tests.

Observe ce que fait l'agent : il lit SKILL.md, lance scope.mjs puis scan.mjs, active les reviewers concernés (en parallèle si ton harness a des sous-agents), fusionne, vérifie chaque candidat, puis rend le rapport.

À la fin : .review/REVIEW.md avec un verdict REQUEST_CHANGES, et .review/findings.json.

Lire le rapport comme un relecteur

  • Le verdict vient du script : compte les BLOCKER et les MAJOR, vérifie la règle.
  • Ouvre un finding BLOCKER et va voir la ligne : l'extrait cité y est-il ?
  • Lis la section « Écartés à la vérification » : chaque rejet a une raison. Es-tu d'accord ?
  • Cherche ce que le skill n'a pas vu : l'étape suivante te dira s'il en manque.

Corriger, puis relancer

Demande « corrige les blockers et les majors » : review-fix prend la main, corrige un finding à la fois, build et test après chacun, et écrit .review/FIXES.md. Relance ensuite la review.

Le verdict doit passer à COMMENT (plus aucun BLOCKER, moins de 3 MAJOR).

Passer le relais

Lance /pr-handoff (dans Claude Code ; ailleurs : « écris la description de PR avec pr-handoff »). Lis .review/PR_BODY.md et .review/HANDOFF.md : est-ce qu'un collègue pourrait reprendre ta branche demain matin avec ça ?

Pour aller plus loin

Trois bonus

Bonus A · ta règle maison

Ajoute une règle R-PROJ-001 dans .agents/skills/angular-review/references/PROJECT_COMPLIANCE_REVIEW.md (par exemple : « chaque page expose un data-testid racine »). Relance : le reviewer projet s'active, et un BLOCKER R-PROJ suffit à demander des changements.

Bonus B · la CI

Sur ton fork, ouvre une PR depuis feat/speaker-spotlight. Le workflow angular-review.yml annote le diff sans IA ; ajoute le secret ANTHROPIC_API_KEY pour la review complète en commentaire.

Bonus C · ton skill

Demande à l'agent « crée un skill pour … » : skill-smith t'interviewe, génère le squelette, et validate.mjs vérifie qu'il respecte le standard. Idée : un skill angular-upgrade-notes qui résume l'impact d'un ng update.
