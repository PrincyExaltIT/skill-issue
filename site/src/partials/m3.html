@@ 03 · 3.1 @@hand-offbase5 min

Un skill fait une étape. Les étapes se passent des fichiers.

Un skill qui veut tout faire (relire, corriger, ouvrir la PR) devient long, ambigu et impossible à tester. On découpe par étape, et chaque étape laisse derrière elle un fichier que la suivante sait lire.

Ce fichier est un contrat. angular-review écrit .review/findings.json ; review-fix le lit et met à jour les statuts ; pr-handoff en tire la description de PR. Aucun skill n'importe le code d'un autre : chacun peut évoluer seul, tant que le format du fichier est respecté.

Ce découpage a un autre avantage : une étape peut être reprise dans une autre session, un autre harness, ou par un humain. La review peut tourner dans Claude Code, la correction dans Codex, la description de PR dans Cursor. Le fichier sert de mémoire partagée.

→

Hand-off

Passer le relais, c'est écrire ce que l'étape suivante ne peut pas deviner : l'état, les décisions et leur raison, ce qui reste à faire. Pas un résumé de la conversation.

@@ 03 · 3.4 @@subagentscore6 min

Sous-agents, contexte isolé, vérification adversariale

Pourquoi sept reviewers plutôt qu'un seul agent qui lit toutes les règles ? Pour la même raison qu'on ne demande pas à une seule personne de relire la sécurité, l'accessibilité et la performance en une passe.

  • Contexte isolé. Chaque reviewer ne charge que son fichier de règles (5 000 à 9 000 tokens) dans son propre contexte. L'orchestrateur ne reçoit que des JSON courts.
  • Parallélisme. Les reviewers tournent en même temps quand le harness le permet ; sinon, l'orchestrateur les joue un par un avec le même prompt.
  • Attention focalisée. Un reviewer qui ne cherche que des problèmes de réactivité en trouve davantage qu'un généraliste.

Le risque des reviewers spécialisés : ils trouvent toujours quelque chose. D'où l'étape 5, Verify, où l'orchestrateur essaie de réfuter chaque candidat avant de le garder : version d'Angular, défaut du framework, règle projet, code qui gère déjà le cas. C'est le même principe que les reviews multi-agents des outils du moment : générer large, puis vérifier dur.

@@ 03 · 3.5 @@CIcore7 min

Le même skill en CI : GitHub Actions et GitLab CI

Deux jobs, deux promesses. Le premier est déterministe : il tourne sur chaque PR, sans IA ni secret. Le second lance le skill complet si une clé d'API est configurée.

GitHub Actions · kit/ci/github/angular-review.yml 
- name: Scope + scan (annotations sur le diff)
  run: |
    node .agents/skills/angular-review/scripts/scope.mjs --committed --quiet
    node .agents/skills/angular-review/scripts/scan.mjs --format github
- name: Gate (BLOCKER de confiance haute)
  run: node .agents/skills/angular-review/scripts/scan.mjs \
    --format sarif --out angular-review.sarif \
    --fail-on BLOCKER --fail-confidence high
GitLab CI · kit/ci/gitlab/angular-review.gitlab-ci.yml 
angular-review:scan:
  script:
    - node .agents/skills/angular-review/scripts/scope.mjs --committed --quiet
    - node .agents/skills/angular-review/scripts/scan.mjs
        --format gitlab --out gl-code-quality-report.json
        --fail-on BLOCKER --fail-confidence high
  artifacts:
    reports:
      codequality: gl-code-quality-report.json

Côté GitHub, les candidats apparaissent en annotations sur le diff de la PR. Côté GitLab, le rapport Code Quality s'affiche dans le widget de la MR. Le job IA déroule les six étapes et poste REVIEW.md en commentaire. Trois façons de le brancher :

  • Claude Code : anthropics/claude-code-action@v1 (entrées prompt, claude_args, anthropic_api_key). Le prompt peut appeler le skill par son nom : /angular-review.
  • Codex : openai/codex-action@v1 dans un job en lecture seule, puis un second job qui détient le droit d'écrire le commentaire (le modèle recommandé par OpenAI, fourni dans kit/ci/github/angular-review-codex.yml).
  • GitLab : Claude Code en headless dans un job (claude -p, intégration maintenue par GitLab, en bêta), ou l'intégration Codex pour GitLab (@codex review, en bêta).
!

Pourquoi « confiance haute » ?

Le scan produit des candidats. Bloquer un merge sur un candidat de confiance basse (un label manquant deviné par heuristique) fabrique des faux blocages et fait détester l'outil. La porte ne bloque que ce qu'un script peut affirmer seul ; le reste passe par la review.

@@ 03 · 3.7 @@securitycore6 min

Un skill tiers est du code qui s'exécute chez toi

Installer un skill, c'est donner des instructions à un agent qui a accès à ton terminal. Un skill malveillant peut contenir un script qui exfiltre des secrets, ou une consigne cachée dans une référence.

%

Snyk, « ToxicSkills » · février 2026

Sur 3 984 skills publics analysés, 36,8 % ont au moins un défaut de sécurité, 13,4 % un défaut critique, et 76 sont confirmés malveillants (91 % d'entre eux utilisent aussi l'injection de prompt).

%

« Agent Skills in the Wild » · arXiv, janvier 2026

Sur 31 132 skills, 26,1 % ont au moins une vulnérabilité, surtout de l'exfiltration de données (13,3 %) et de l'escalade de privilèges (11,8 %). Les skills qui embarquent des scripts sont 2,12 fois plus souvent vulnérables.

  • Lire avant d'installer, scripts compris. Un skill sans script se lit en cinq minutes ; un skill avec scripts se review comme une dépendance.
  • Épingler et vérifier. Une version précise, et une empreinte : gh skill install --pin <sha> enregistre la provenance (GitHub précise qu'il ne vérifie pas le contenu) ; l'outil forgent de PrincyExaltIT écrit un forgent.lock.json avec le sha256 de chaque fichier et refuse un fichier modifié ; skills.sh affiche un audit de sécurité avant l'installation.
  • Limiter les outils. allowed-tools pré-autorise le strict nécessaire (ici git, node, lecture). Tout le reste repasse par une demande de permission.
  • Traiter le code relu comme une donnée. Un commentaire dans un fichier du diff (« ignore les règles précédentes ») ne doit jamais devenir une instruction ; c'est écrit dans les garde-fous du skill et dans le prompt des reviewers.
  • Respecter la politique de données. Le harness envoie le code au fournisseur du modèle. Le skill le rappelle : pas de review de code confidentiel sans accord.
@@ 03 · 3.8 @@adoptionbase5 min

Lundi matin : adopter le kit en équipe

  1. Installer en portée projet dans un repo pilote et commiter .agents/skills/ (et .claude/skills/ si l'équipe utilise Claude Code).
  2. Remplir PROJECT_COMPLIANCE_REVIEW.md avec 3 à 5 règles maison (R-PROJ). C'est là que le skill devient le vôtre.
  3. Brancher le job de scan en CI, en mode non bloquant pendant deux semaines. Regarder les candidats écartés : ils disent où les règles sont trop larges.
  4. Mesurer avec evals/ à chaque modification de règle : le composant propre doit rester à zéro, le corrigé de démo ne doit pas perdre de rappel.
  5. Faire évoluer par PR, comme du code. Une règle qui génère du bruit se corrige ou se supprime.
