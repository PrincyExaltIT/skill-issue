Le 8 octobre 2026, on a lancé exactement la même phrase, « Fais une review de cette branche avant que je la merge sur main », sur la branche de démo, avec le skill installé tel quel. Une fois dans Claude Code, une fois dans Codex. Puis on a noté les deux rapports contre le corrigé.

Ce que ces chiffres disent, et ce qu'ils ne disent pas

  • Le skill est portable pour de vrai. Aucune ligne modifiée entre les deux harnesses : Claude Code l'a lu dans .claude/skills, Codex dans .agents/skills.
  • Le jugement fait la différence sur ce que le scan ne voit pas : la route chargée sans lazy loading, le lien entre une bio rendue en HTML et le formulaire qui annonce « HTML autorisé », des correctifs écrits pour ce code-là et pas pour un exemple générique.
  • Les sévérités dérivent d'un modèle à l'autre (2 BLOCKER d'un côté, 8 de l'autre). Le verdict est calculé, mais à partir de sévérités choisies par des modèles. Depuis ce banc d'essai, findings.mjs trace chaque re-notation d'un candidat par un reviewer.
  • L'eval a trouvé une faille dans le skill : Claude a regroupé un any du service sous le finding d'un autre fichier. Une phrase ajoutée à l'étape Verify (« regrouper seulement dans un même fichier ») corrige le comportement. Mesurer, corriger, re-mesurer : c'est la boucle.
  • Le corrigé n'a pas toujours raison. Les deux agents ont écarté la « fuite » de valueChanges sur un formulaire détenu par le composant, avec un argument juste. Le point est désormais marqué discutable dans le corrigé.
  • Le scan à 96 % est optimiste : la branche de démo et le scan ont été écrits par la même équipe. Sur un vrai projet, compte sur le scan pour le mécanique, et sur les reviewers pour le reste.

Les deux rapports complets, leurs findings.json et leurs scores sont dans docs/sample-review/ du kit. Pour rejouer : étapes 4 à 6 du lab.
