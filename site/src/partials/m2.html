@@ 02 · 2.4 @@step by stepcore14 min

Construire le skill, en six décisions

1 · Le métier, puis la description

On écrit d'abord ce que le skill fait en une phrase, puis les situations où on veut qu'il se déclenche. La description est écrite en dernier, mais pensée en premier : elle conditionne tout le reste.

2 · Un workflow avec des critères de fin

Le corps de SKILL.md est une suite d'étapes, chacune terminée par une condition vérifiable. « Done when findings.mjs list --status candidate prints nothing » vaut mieux que « vérifie soigneusement » : l'agent sait quand il a fini, et ne saute pas l'étape pour arriver plus vite à la suivante.

### 5. Verify
Take each candidate and try to **refute** it: version gates, framework defaults,
project rules, code elsewhere that already handles the case, a path that cannot run.
[…]
Done when `node scripts/findings.mjs list --status candidate` prints nothing.

3 · Les scripts : ce qui doit être exact

Trois scripts Node sans dépendance, chacun avec un rôle unique :

$ node scripts/scope.mjs
[scope] Angular 22.2.1 | working-tree | 15 file(s) (+466 -2) | base=main -> .review/scope.json
$ node scripts/scan.mjs

BLOCKER R-ARCH-017  src/app/proposals/proposal-form.ts:47  subscribe sans désabonnement dans un composant/directive
BLOCKER R-A11Y-005  src/app/speakers/speaker-spotlight.html:22  (click) sur un élément non interactif
BLOCKER R-SIG-005   src/app/speakers/speaker-spotlight.ts:30  API à contexte d'injection appelée hors contexte (NG0203)
…
[scan] 44 candidat(s) — BLOCKER:8 MAJOR:11 MINOR:22 INFO:3 — .review/scan.json
$ node scripts/findings.mjs merge && node scripts/findings.mjs render

Sortie réelle sur la branche de démo feat/speaker-spotlight (8 octobre 2026). Le lab te fait obtenir la tienne.

4 · Les références : un fichier par reviewer

Sept domaines, chacun avec un frontmatter applies_to (les fichiers qui l'activent) et un préfixe de règles. L'orchestrateur n'active que les reviewers concernés par le diff, et chacun ne charge que son fichier. Le format d'une règle reste celui de la v1 :

### R-SIG-005 — API à contexte d'injection appelée hors contexte (NG0203)
- **Sévérité** : 🔴 BLOCKER
- **Quoi vérifier** : inject(), toSignal(), effect() et takeUntilDestroyed() sans argument
  exigent un contexte d'injection […]
- **Exemple ❌** / **Exemple ✅** / **Source** : https://angular.dev/errors/NG0203

5 · Un contrat de sortie

Les reviewers écrivent du JSON validé (ruleId, severity, file, line, snippet, message, suggestion…). Le rapport humain est généré à partir de ce JSON, jamais l'inverse : la machine et l'humain lisent la même vérité.

6 · Des evals

Trois niveaux de tests, rangés hors du dossier du skill pour ne jamais être chargés par l'agent : snapshots du scan sur des fixtures (dont un composant propre qui doit rester à zéro), prompts de déclenchement, et un corrigé de la branche de démo pour mesurer le rappel et la précision d'une review complète.

Le déclenchement se mesure comme le recommande agentskills.io : chaque prompt rejoué trois fois en headless, déclenché si le taux atteint 0,5, avec autant de quasi-positifs (« crée un composant », « review mon composant React ») que de positifs. run-triggers.mjs le fait avec claude -p ; Claude Code propose aussi claude plugin eval, qui compare chaque cas avec et sans le skill.

L'histoire d'OnPush, ou pourquoi un skill doit connaître sa version

Jusqu'à Angular 21, un composant sans ChangeDetectionStrategy.OnPush méritait une remarque. Angular 22 a inversé le défaut : OnPush s'applique sans rien écrire, et ng update ajoute ChangeDetectionStrategy.Eager aux composants qui dépendaient de l'ancien comportement. La même règle, appliquée telle quelle, signale désormais chaque composant correct. La v2 lit la version installée, et sur Angular 22 elle cherche l'inverse : les Eager non justifiés.

✓

Test terrain · projet de formation playing-cards, Angular 21.2

Le scan sort 10 candidats en 90 ms, tous réels : un champ de recherche sans label, un output nommé submit comme l'événement natif, un transform d'input qui double les points de vie en mutant l'objet du parent, OnPush absent (à juste titre en v21), des specs qui ne testent que la création. Aucun faux positif. Les imports inutilisés, les readonly manquants et le nommage restent le travail des reviewers.

Laisser au lint ce qui est au lint

Si le projet utilise angular-eslint, beaucoup de règles mécaniques sont déjà appliquées en CI (prefer-control-flow, prefer-inject, template/alt-text, no-output-native…). Chaque détecteur du scan porte le nom de la règle eslint équivalente : quand le lint est installé, le skill écarte ces candidats et garde son attention pour ce qu'aucun lint ne voit (un effect qui synchronise de l'état, une resource utilisée pour écrire, une bio utilisateur rendue sans sanitizer).

@@ 02 · 2.6 @@installcore6 min

Installer partout, versionner avec le projet

Deux portées : projet (le dossier est commité avec le code, toute l'équipe l'a) ou utilisateur (dans ton home, disponible dans tous tes projets). Pour un skill d'équipe, la portée projet gagne : le skill évolue avec le code qu'il review.

# depuis le clone du kit : installe les 4 skills dans le projet cible, pour tous les harnesses
$ node kit/install.mjs --target ../mon-projet-angular
# seulement Claude Code et Codex, en liens symboliques (les mises à jour du kit se propagent)
$ node kit/install.mjs --target ../mon-projet-angular --harness claude,codex --mode link
# en portée utilisateur
$ node kit/install.mjs --scope user --skills angular-review
# avec l'installeur communautaire de Vercel (liens symboliques par défaut, --copy pour copier)
$ npx skills add PrincyExaltIT/skill-issue
# avec la CLI GitHub (aperçu), en épinglant une version
$ gh skill install PrincyExaltIT/skill-issue --pin v1.0.0

npx skills envoie de la télémétrie par défaut (désactivable avec DISABLE_TELEMETRY=1) et, depuis la version 1.4, affiche l'audit de sécurité skills.sh avant d'installer.

L'installeur lit kit/harnesses.json, copie chaque dossier de skill tel quel (sans transformation), puis vérifie chaque installation avec le validateur de skill-smith. --dry-run montre ce qu'il ferait sans rien écrire.

!

Copie ou lien ?

La copie est sûre et portable (Windows sans droits admin, CI). Le lien symbolique évite les versions divergentes quand tu développes le skill lui-même. En équipe : copie commitée dans le repo, mise à jour par PR.
