Étape 1 · De l'intention à la procédure

« Relis ma branche » est une intention. Une procédure dit dans quel ordre travailler, sur quoi, et quand une étape est finie. Sans elle, le relecteur fait ce qu'il veut ; avec, on peut compter sur lui.

La version 1 découpe la review en quatre étapes, et chacune se termine par un critère de fin que l'agent peut vérifier seul. De toutes les idées de Matt Pocock pour écrire des documents d'agent, c'est celle qui rapporte le plus. Un critère flou (« bien comprendre le code ») invite à bâcler pour passer à la suite ; un critère vérifiable (« chaque fichier de la liste a été lu en entier ») force le travail.

## 1. Délimiter le périmètre
git diff main...HEAD -- . ':!.claude' ':!.agents' ':!.review'
Fini quand : tu as la liste des fichiers modifiés et, pour chacun, les lignes ajoutées ou modifiées.

## 2. Lire chaque fichier modifié en entier
Fini quand : chaque fichier de la liste a été lu en entier.

## 3. Chercher les problèmes (six familles : bugs, sécurité, réactivité, a11y, conventions, tests)
Fini quand : chaque fichier a été passé au crible des six familles.

## 4. Écrire le rapport (gabarit assets/rapport.md, gravités, règle de verdict)
Fini quand : .review/REVIEW.md existe, chaque finding cite fichier:ligne, les compteurs correspondent.

Dans le lab, la base s'appelle depart : ta demande la nomme (« avant que je la merge sur depart ») et l'agent remplace main. À partir de l'étape 3, le script prend tout seul la branche par défaut du dépôt.

Trois choix de conception à retenir :

  • Le périmètre est le diff. L'agent relit les lignes que la branche ajoute ou modifie ; le reste du projet sert de contexte. Les dossiers d'outillage (.claude, .agents, .review) sortent du diff : ton skill ne se relit pas lui-même.
  • Le rapport a un gabarit. assets/rapport.md fixe la forme : verdict, compteurs, un bloc par finding. Un gabarit dans assets/ n'est lu qu'au moment d'écrire : c'est le troisième étage du chargement progressif.
  • Le verdict suit une règle écrite. À corriger dès un BLOCKER ou trois MAJOR. Une règle écrite, l'équipe peut en débattre, alors qu'une impression ne se discute pas.

Étape 2 · Les règles de ton équipe, chargées à la demande

Le modèle connaît Angular, mais pas les décisions de ton équipe : ce qu'elle tolère, ce qu'elle refuse, et pourquoi. Pour un skill de review, c'est ce qu'il y a de plus utile à lui apprendre.

Les règles vont dans references/, un fichier par domaine : angular-22.md, reactivite.md, securite.md, accessibilite.md, tests.md. Chaque règle a le même format court :

### SIG-04 · API à contexte d'injection appelée hors contexte (NG0203) — BLOCKER
**Pourquoi** : inject(), takeUntilDestroyed() sans argument, toSignal() et effect() exigent un
contexte d'injection. Dans ngOnInit, une méthode ou un callback, ils lèvent NG0203.
**À repérer** : ces appels dans un hook ou une méthode. takeUntilDestroyed(this.destroyRef)
avec un DestroyRef injecté fonctionne partout.
**Correction** : déplacer l'appel dans un initialiseur de champ, ou passer DestroyRef explicitement.

Le SKILL.md ne recopie pas les règles, il dit seulement quand charger chaque fichier. Un diff qui ne touche aucun template ne charge pas l'accessibilité. Voilà le chargement progressif appliqué à ta review :

| Le périmètre contient                                   | Charge                        |
|---------------------------------------------------------|-------------------------------|
| des composants, services, routes ou formulaires         | references/angular-22.md      |
| des signals, effect, subscribe, setTimeout, appels HTTP | references/reactivite.md      |
| du HTML injecté, des URL, du stockage, des redirections | references/securite.md        |
| des templates (.html ou template:)                      | references/accessibilite.md   |
| de nouveaux fichiers ou des .spec.ts                    | references/tests.md           |

Écrire de bonnes règles

  • Pars de tes vraies reviews. Les dix remarques que ton équipe répète dans les PR sont tes dix premières règles.
  • Pas d'équipe sous la main ? Prends deux sources. D'abord les conventions du AGENTS.md du lab (signals, input() et output(), inject(), control flow natif, NgOptimizedImage). Ensuite le menu ci-dessous : des règles candidates tirées des références de l'étape 2.
  • Écris aussi ce qui n'est pas un problème. « Un composant sans changeDetection est déjà en OnPush (v22) : rien à signaler » évite un faux positif à chaque PR.
  • Date tes faits. En Angular 22, OnPush est le défaut, ChangeDetectionStrategy.Eager remplace Default, et les *ngIf sont dépréciés depuis la v20. Une règle écrite pour la v17 donne de mauvais conseils en v22.
  • AGENTS.md prime. Les conventions toujours vraies du dépôt y sont déjà ; tes références les détaillent pour la review, sans les contredire.

Un relecteur qui signale tout ne sert à rien, parce que l'équipe arrête de le lire. Reste à apprendre à ta review la dernière qualité : écarter ce qui ressemble à un problème sans en être un.

Tu ajoutes deux choses. ## 6. Vérifier : réfuter chaque finding
- Périmètre : la ligne est-elle ajoutée ou modifiée par la branche ? Sinon, elle sort du rapport.
- Preuve : le code fait-il vraiment ce que tu affirmes ? Suis l'appel jusqu'au bout.
- Déjà couvert : le framework ou le projet gère-t-il le cas ? Compare avec les pièges de assets/exemples.md.
- Doublon : un finding par problème et par fichier ; les autres lignes vont dans sa note.
Fini quand : chaque finding est gardé, fusionné ou écarté avec une raison.

Étape 5 · Un seul dossier pour toute l'équipe et tous les harnesses

Un skill dans ton home ne sert qu'à toi. Commité dans le dépôt, il sert à toute l'équipe, évolue avec le code qu'il relit, et se change par pull request comme le reste.

Ton outil n'est pas dans la matrice ?

La matrice donne des exemples, et la liste n'est pas fermée : ton équipe utilise peut-être un autre harness, ou un outil maison. Dans ce cas, trois vérifications suffisent.

  3. Il ne connaît pas les skills ? Mets un pointeur dans son fichier d'instructions (AGENTS.md ou son équivalent) : « Pour relire une branche, suis .agents/skills/revue-angular/SKILL.md. » Les scripts, eux, tournent partout : ce sont des scripts Node sans dépendance.
