@@ 01 · 1.1 @@modèle, agent, harnessbase6 min

Le modèle ne lit pas tes fichiers. Le harness, si.

Un modèle de langage fait une seule chose : il lit un texte et prédit la suite. Il ne voit pas ton disque, n'exécute rien, ne se souvient de rien entre deux appels.

Tout le reste est fait par le harness : le programme qui entoure le modèle. Claude Code, Codex, Cursor, Copilot, Gemini CLI sont des harnesses. À chaque tour, le harness assemble le contexte (instructions système, mémoire du projet, descriptions des skills, conversation), l'envoie au modèle, lit la réponse, et si le modèle demande un outil (lire un fichier, lancer une commande, appeler un serveur MCP), il l'exécute avec tes permissions puis renvoie le résultat. Cette boucle, c'est ce qu'on appelle un agent.

!

À retenir

Même modèle, harness différent : comportement différent. Et c'est parce qu'un skill n'est qu'un dossier de fichiers lus par le harness qu'il peut passer d'un outil à l'autre.

@@ 01 · 1.2 @@context windowbase6 min

Le contexte est un budget, pas un sac

Tout ce que l'agent « sait » pendant une tâche tient dans sa fenêtre de contexte : instructions système, définitions d'outils, fichiers de mémoire, schémas MCP, conversation, fichiers lus, sorties de commandes.

Chaque token coûte trois fois : en argent, en latence, et en qualité. Plus le contexte est long et hétérogène, plus l'attention du modèle se dilue ; on parle parfois de context rot. Un CLAUDE.md de 900 lignes qui explique la review, les migrations, les releases et le style CSS est lu à chaque tour, même pour renommer une variable.

La réponse des skills : ce qui est toujours chargé doit être minuscule, tout le reste se charge à la demande. Joue avec le nombre de skills installés :

Simulateur · fenêtre de 200 000 tokens
■ Progressive disclosure : 0 tokens (toutes les descriptions + 2 skills actifs)
■ Tout charger d'avance : 0 tokens, soit 0 % de la fenêtre avant d'avoir lu une ligne de ton code

Hypothèses du simulateur : environ 100 tokens par description (l'ordre de grandeur du standard) et environ 4 500 tokens par corps de skill (le standard recommande moins de 5 000). Le skill que tu vas construire est bien plus léger : environ {{TAILLE:n1}} tokens au niveau 1 et environ {{TAILLE:n2}} au niveau 2 (voir la leçon 1.4).

@@ 01 · 1.3 @@anatomiebase8 min

Un skill est un dossier

La définition du standard tient en une phrase : un dossier qui contient un fichier SKILL.md, et éventuellement des scripts, des références et des ressources.

SKILL.md commence par un frontmatter YAML, puis des instructions en Markdown. Deux champs sont obligatoires : name (64 caractères max, minuscules, chiffres et tirets, identique au nom du dossier) et description (1 024 caractères max). Le standard prévoit aussi license, compatibility, metadata et, à titre expérimental, allowed-tools. Chaque harness peut ajouter ses propres champs ; les autres les ignorent.

Clique dans l'arborescence du skill que tu vas construire pendant la formation, revue-angular, dans sa version finale. L'étiquette indique quand chaque fichier entre dans le contexte.

Explorateur · course/revue-angular/etape-5
AR

Pourquoi pas un gros prompt ?

Un prompt se copie-colle, se perd et dérive. Un dossier se versionne, se review, se teste et s'installe. Le skill a un cycle de vie de code.

@@ 01 · 1.5 @@description = triggercore7 min

La description fait tout le déclenchement

Avant de décider, le modèle ne voit que la description. Si elle est floue, le skill ne se déclenche pas, ou se déclenche à tort.

Une bonne description fait deux choses : elle dit ce que fait le skill, puis elle liste les cas où l'utiliser, avec les mots que tes collègues tapent vraiment. Matt Pocock parle de « pointeur de contexte » : une référence qui nomme un contenu hors contexte. La formulation de la description décide donc quand l'agent ira chercher ce contenu. D'où trois règles :

  • Mettre les mots déclencheurs en tête (review, audit, PR/MR).
  • Un déclencheur par cas réel ; les synonymes d'un même cas ne font qu'ajouter du bruit.
  • Écrire à la troisième personne, sans répéter ce que le corps détaille.

Les harnesses rationnent cet espace. Claude Code plafonne la liste des skills à 1 % de la fenêtre et tronque la description (avec when_to_use) à 1 536 caractères. Codex limite la liste à 2 % de la fenêtre au plus, ou à 8 000 caractères quand la taille est inconnue. Une description bavarde n'est pas seulement inefficace, elle peut être coupée.

# avant : vague, aucun cas d'usage
- description: Aide sur la qualité du code Angular.
# après : ce que ça fait + quand l'utiliser
+ description: Revue de code Angular des changements d'une branche, d'une PR ou
+   d'une MR, selon les règles de l'équipe. À utiliser quand on demande de relire,
+   reviewer ou vérifier du code Angular avant un merge.

@@ 01 · 1.6 @@degrees of freedomcore6 min

Prose ou script ? Régler le degré de liberté

Une instruction en prose laisse le modèle juger. Un script ne lui laisse rien. Les deux sont utiles, à des endroits différents.

✎

Prose · liberté haute

Ce qui demande du jugement : est-ce que cet effect est un vrai effet de bord ? Ce subscribe peut-il fuir ? Ce composant est-il trop gros ?

{}

Script · liberté nulle

Ce qui doit être exact, répétable ou vérifiable : le périmètre du diff, les numéros de ligne, le schéma de sortie, le verdict, les formats CI.

Dans le skill que tu vas construire, la règle « pas de console.log oublié » existe d'abord en prose, à l'étape 2, dans references/angular-22.md (règle NG-05) : le modèle la lit, et la suit quand il y pense. À l'étape 3, la même règle devient une ligne de la table REGLES de scripts/verifs.mjs :

{ id: 'NG-05', gravite: 'MINOR', fichiers: TS, motif: /\bconsole\.(log|debug)\s*\(|\bdebugger\b/g,
  message: 'Trace de débogage oubliée.' },

Le script trouve chaque occurrence sur les lignes modifiées, à chaque run, en moins d'une seconde. Le modèle n'a plus qu'à confirmer ou à écarter la piste en lisant le code. Même idée pour la porte de CI : ce n'est pas une phrase en majuscules dans SKILL.md, c'est un code de sortie.

if (seuil && pistes.some((p) => GRAVITES.indexOf(p.gravite) <= GRAVITES.indexOf(seuil))) {
  console.error(`Porte fermée : au moins une piste ${seuil} ou plus grave.`);
  process.exit(1);
}

Un MUST en majuscules dans un skill est souvent le signe d'une étape qui devrait être du code.

Au module 2, c'est l'étape 3 : perimetre.mjs lit le diff à la place du modèle, verifs.mjs repère les motifs connus, et le modèle garde le jugement.

@@ 01 · 1.7 @@écosystèmecore8 min

Skill, AGENTS.md, MCP, sous-agent, hook : qui fait quoi

Les skills ne remplacent rien. Ils prennent une place précise à côté des autres briques du harness.

BriqueChargéeSert àDans ta review
AGENTS.md / CLAUDE.mdToujoursCe qui est toujours vrai dans ce repo : stack, commandes, conventionsLes conventions du dépôt de démo, que ta revue applique
SkillDescription toujours, le reste à la demandeUn savoir-faire procédural réutilisablerevue-angular, que tu construis
Serveur MCPSchémas d'outils au démarrage, appels à la demandeAccéder à un système : API, navigateur, ticketingLe serveur MCP d'Angular CLI ou celui de Playwright, en option
Sous-agentÀ la demande, dans un contexte séparéParalléliser, isoler une tâche bavardeUn relecteur par domaine (module 3)
HookSur un événement, sans passer par le modèleCe qui doit arriver à coup sûr : format, lint, garde-fousverifs.mjs après chaque édition de l'agent (module 3)
Commande slashÀ la mainUn raccourci de prompt/revue-angular : le même skill, appelé par son nom

MCP en trois points

  • Ce qu'un serveur expose. Des outils (des fonctions que le modèle appelle), des ressources (des données en lecture, que l'application verse au contexte) et des prompts (des modèles d'instructions que tu invoques toi-même). Le serveur MCP d'Angular (npx -y @angular/cli mcp) expose par exemple get_best_practices et search_documentation.
  • Qui approuve un appel. Le harness, avec ses permissions, pas le serveur. Le protocole laisse au harness le soin de demander ton accord. En CI, personne ne clique : c'est la liste d'outils autorisés (--allowedTools, avec des noms comme mcp__gitlab) qui décide. Dans une routine Claude Code, les outils des connecteurs, écritures comprises, tournent sans demande de permission.
  • Une règle de sécurité. Un serveur MCP est du code que tu lances avec tes droits. C'est la même règle de confiance que pour un skill tiers (module 3) : tu le lis, tu épingles sa version, et tu retires ce dont le run n'a pas besoin.
→

Règle de poche

Toujours vrai : AGENTS.md. Une procédure : un skill. Un accès à un système : MCP. Doit arriver à coup sûr : un hook. Trop gros pour le contexte principal : un sous-agent.

@@ 01 · 1.8 @@invocationdeep5 min

Qui appuie sur le bouton : l'agent ou toi ?

Un skill déclenché par le modèle coûte sa description dans chaque session. Un skill déclenché à la main ne coûte rien en contexte, mais c'est toi qui dois te souvenir qu'il existe.

Matt Pocock formalise ce choix dans son skill writing-for-agents (dépôt mattpocock/skills, état du 9 octobre 2026 : les noms de ses skills changent vite) : la charge de contexte pèse sur la fenêtre de l'agent, la charge cognitive pèse sur l'humain, qui doit savoir quels documents existent et quand les prendre. Quand les skills manuels deviennent trop nombreux pour s'en souvenir, il passe par un router skill : un seul skill manuel qui sert d'index aux autres (dans son dépôt, ask-matt).

Ta revue se déclenche seule : c'est ce qu'on veut quand quelqu'un demande « tu peux relire ma PR ? ». Dans le package de Princy, pr-handoff est au contraire manuel, parce qu'écrire la description d'une PR est une décision. Dans Claude Code, cela s'écrit avec un champ propre au harness :

---
name: pr-handoff
description: Write the pull/merge request description and a handoff note […]
disable-model-invocation: true   # extension Claude Code : invocation par /pr-handoff uniquement
---
HarnessRendre un skill manuel
Claude Code, Cursor, Copilot (VS Code)disable-model-invocation: true dans le frontmatter
Codexagents/openai.yaml → policy: allow_implicit_invocation: false (le skill reste appelable par $pr-handoff)
Gemini CLIL'utilisateur valide de toute façon chaque activation
OpenCodepermission.skill : ask ou deny par skill
!

Le prix d'une extension

Un champ hors standard est ignoré par les harnesses qui ne le connaissent pas, mais il est refusé par le validateur officiel skills-ref et par l'upload sur claude.ai. Deux stratégies : un SKILL.md strictement standard, avec le comportement réglé dans la configuration de chaque harness (agents/openai.yaml, réglages Claude Code) ; ou des champs d'extension, plus simples pour l'équipe mais non publiables tels quels. validate.mjs --strict te dit dans quel camp est ton skill.

Assez de théorie. Tu vas écrire le plus petit skill qui marche, le lancer sur une vraie pull request, et le noter. Ce score de départ, tu vas le faire monter pendant tout le module 2.

Si un clone répond « not found », le dépôt n'est pas encore ouvert à ton compte : demande un accès en lecture à PrincyExaltIT.

La branche lab/speaker-spotlight est une pull request écrite dans l'urgence : une page speaker et un formulaire de proposition de talk, en Angular 22. Elle compile. Elle n'est pas prête. Le second dépôt contient le corrigé, rangé hors de portée de l'agent qui relit.

2 · Le skill

Crée .claude/skills/revue-angular/SKILL.md (Claude Code, Continue) ou .agents/skills/revue-angular/SKILL.md (Codex, Copilot, Cursor, Gemini CLI, OpenCode, Kilo Code) :

---
name: revue-angular
description: Revue de code Angular des changements d'une branche, d'une PR ou d'une MR. À utiliser quand on demande de relire, reviewer ou vérifier du code Angular avant un merge.
---

# Revue Angular

Relis les changements de la branche courante par rapport à sa branche de base : `main`, ou celle que l'utilisateur nomme.

Pour chaque problème, donne :
- l'emplacement `chemin/du/fichier.ts:ligne` ;
- la gravité : BLOCKER, MAJOR, MINOR ou INFO ;
- le problème et la correction proposée.

Écris le rapport dans `.review/REVIEW.md` et termine par un verdict : à merger, à discuter ou à corriger.
