Ce qu'il y a dans la boîte

Un dépôt, zéro dépendance externe : quatre skills, un installeur pour les harnesses de la matrice (huit à ce jour), deux pipelines CI, un hook, des gabarits et des evals.

skill-issue/ ├─ skills/ # les 4 skills du package, au standard agentskills.io │ ├─ angular-review/ # la review : scripts (scope, scan, findings), 10 références, 7 relecteurs │ ├─ review-fix/ # corrige les findings un par un, build et test après chacun │ ├─ pr-handoff/ # description de PR/MR et note de passation (invocation manuelle) │ └─ skill-smith/ # crée et valide des skills : new-skill.mjs, validate.mjs ├─ kit/ │ ├─ install.mjs # installe dans .agents/skills, .claude/skills… (copie ou lien) │ ├─ harnesses.json # où chaque harness cherche ses skills, daté │ ├─ ci/github/ # scan sans IA (annotations, résumé, porte), review IA Claude ou Codex │ ├─ ci/gitlab/ # Code Quality dans la MR, note IA optionnelle │ ├─ hooks/ # Claude Code : scan après chaque édition de l'agent │ └─ templates/ # AGENTS.md et CLAUDE.md pour un projet Angular ├─ course/ # la formation : revue-angular étape par étape, rattrapage, CI du bonus cloud ├─ evals/angular-review/ # fixtures, snapshots, corrigé de la démo, score.mjs, run-triggers.mjs ├─ docs/sample-review/ # reviews réelles, notées : package, chaîne, formation ├─ site/ # cette formation (un seul fichier HTML généré) └─ studio/ # les vidéos : scènes HTML rendues image par image

La chaîne et la CI, en vrai

Le 8 octobre 2026, la chaîne complète du package a tourné sur la PR de démo. Elle a corrigé beaucoup, et elle a eu l'honnêteté de dire qu'il ne fallait pas merger.

ÉtapeHarnessRésultatDurée · coût
angular-reviewCodexREQUEST_CHANGES 8 BLOCKER, 13 MAJOR, 16 MINOR≈ 12 min · quota ChatGPT
review-fix (BLOCKER + MAJOR)Claude Code21 commits, un par finding, chacun avec un test de régression21 min · 6,08 $
angular-review (re-review)Claude CodeREQUEST_CHANGES 1 BLOCKER, 2 MAJOR, 15 MINOR2,7 min · 5,69 $
pr-handoffClaude CodeDescription de PR « à ne pas merger en l'état », décisions listées pour l'humain1,7 min · 0,71 $

Deux leçons. Le contrat suffit au relais : Codex a écrit findings.json, Claude Code l'a lu et corrigé, sans adaptation. La chaîne ne merge pas à ta place : l'URL d'API en dur, classée MINOR au premier tour, devient le BLOCKER de la re-review, et deux MAJOR sont nés des corrections elles-mêmes. Le résultat est sur la branche solution/review-fix (PR #2).

C'est la chaîne du package de Princy : angular-review, review-fix, pr-handoff, avec un contrat findings.json. Ta propre chaîne, plus courte, se construit dans le module 3 (atelier 6).

Ce que la vraie CI du package nous a appris

  • La porte fait ce qu'elle promet. Sur la PR #1, 44 candidats, mais un seul BLOCKER de confiance haute (R-SIG-010, talk-card.ts:28), et le job échoue. Sur la branche corrigée, la porte passe, alors que la re-review trouve encore un BLOCKER.
  • Les annotations sont plafonnées. Sur nos runs, GitHub n'en a affiché que dix par niveau et par étape : 9 MAJOR sur 11 manquaient. D'où le tri par sévérité et le résumé du job, qui liste tout.
  • Le SARIF a ses conditions. L'upload demande la permission actions: read, et le code scanning d'un dépôt privé demande GitHub Code Security : le package n'envoie le SARIF que sur un dépôt public, ou si ANGULAR_REVIEW_SARIF vaut true.
  • Les avertissements vieillissent vite. Sur nos runs, GitHub a signalé des actions encore en Node 20 (dépréciées) et CodeQL v3 en fin de vie en décembre 2026 : le package est passé à checkout@v7, setup-node@v7 et upload-sarif@v4.

L'adopter en équipe

# seulement Claude Code et Codex, en liens symboliques (les mises à jour du package se propagent)
$ node kit/install.mjs --target ../mon-app --harness claude,codex --mode link
# en portée utilisateur, pour tous tes projets
$ node kit/install.mjs --scope user --skills angular-review
# où chaque harness cherche ses skills
$ node kit/install.mjs --list
  1. Ajoute tes règles maison dans references/PROJECT_COMPLIANCE_REVIEW.md (préfixe R-PROJ) : le relecteur projet s'active dès la première règle, et un BLOCKER R-PROJ suffit à demander des changements. Reprends celles de ton skill : le format diffère un peu, la conversion tient en trois lignes.
    1. Titre : ### SIG-04 · titre — BLOCKER devient ### R-PROJ-001 — titre (préfixe R-PROJ- et trois chiffres, « — » au lieu de « · », plus de gravité dans le titre).
    2. Gravité : le mot de fin de titre passe sur sa propre ligne, - **Sévérité** : 🔴 BLOCKER (🟠 MAJOR, 🟡 MINOR, 🔵 INFO).
    3. Corps : ton À repérer devient - **Quoi vérifier** : (et - **Pattern à flag** : s'il y a un motif), ta Correction devient - **Exemple ✅** :, ton Pourquoi devient - **Note** :. Ajoute - **Référence** :, la source de la règle (une ligne de ton AGENTS.md, par exemple).
    Place-les sous « Règles à vérifier », en dehors du commentaire d'exemple : le relecteur projet ne s'active que s'il trouve au moins une règle.
  2. Branche la CI en mode non bloquant pendant deux semaines, et lis les candidats écartés : ils disent où les règles sont trop larges.
  3. Mesure à chaque modification de règle avec evals/ : le composant propre doit rester à zéro, le corrigé de démo ne doit pas perdre de rappel.
  4. Sur GitLab : glab auth login, puis bash kit/gitlab-mirror.sh <groupe> pour recopier le dépôt, et inclure kit/ci/gitlab/angular-review.gitlab-ci.yml. Ce gabarit n'a pas été exécuté à ce jour : lis-le avant de t'y fier.
