**Contradictions à retenir**

- Gains déclarés (c2, c9) contre débit et stabilité en baisse en 2024 (c3) ; en 2025, débit corrélé positivement mais instabilité en hausse (c12).
- Gains mesurés en entreprise (c31) et sur tâches isolées (c29) contre ralentissement mesuré sur des dépôts matures (c23), avec une perception de gain dans les deux cas (c24).
- METR 2026 n'est pas un « renversement » établi : le sens du signe est ambigu et les intervalles contiennent zéro (c26 à c28).
- Stack Overflow : 29 % ou 33 % de confiance selon la source (c17) ; favorabilité 72 % ou plus de 70 % selon la source (c16).

## 2. Pratiques d'adoption qui fonctionnent

- **c45.** GitHub : commencer par un petit nombre d'équipes volontaires pour tester le processus d'accompagnement avant le déploiement large ; le pilote sert à ajuster, pas seulement à valider. Source : https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/enable-developers/drive-adoption — VERIFIED
- **c46.** GitHub : les champions sont recrutés dans le pilote parmi les utilisateurs enthousiastes qui aident les autres, et participent à la création des formations et ressources. Source : https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/enable-developers/drive-adoption — VERIFIED
- **c47.** GitHub, calendrier type : 45 jours avant le lancement (définir les métriques de succès, former les champions), 14 jours (annonces et ressources asynchrones), 7 jours (atelier), jour J (canal dédié, wiki). Source : https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/enable-developers/drive-adoption — VERIFIED
- **c48.** GitHub : définir dès le départ « quelques métriques qui comptent » (par exemple des PR plus rapides ou moins de questions « comment démarrer ? ») et suivre l'activation des licences en relançant les inactifs. Source : https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/enable-developers/drive-adoption — VERIFIED
- **c49.** GitHub : formation d'abord en séances formelles, dont un sprint d'onboarding où les développeurs travaillent en binôme sur du travail réel, puis aide à la demande à mesure que l'adoption progresse. Source : https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/enable-developers/drive-adoption — VERIFIED
- **c50.** GitHub : boucles de retour régulières (un point « Copilot » dans les rétrospectives). Le guide ne décrit pas de paliers d'accès ni de calendrier d'ouverture ; il cite la licence en libre-service comme alternative à l'approbation par étapes. Source : https://docs.github.com/en/copilot/tutorials/roll-out-at-scale/enable-developers/drive-adoption — VERIFIED
- **c51.** DORA 2024, recommandations de Google : établir des lignes directrices claires sur l'usage de l'IA, favoriser une communication ouverte sur ses effets, et accorder du temps à l'expérimentation pour construire la confiance. Source : https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report — VERIFIED
- **c52.** DORA AI Capabilities : un stance IA clair et communiqué amplifie l'impact positif de l'IA. La capacité ne mesure pas le contenu de la politique, mais sa clarté et sa diffusion. Source : https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model — VERIFIED
- **c53.** DORA AI Capabilities : le travail en petits lots, « un principe DORA de longue date », est « particulièrement puissant dans un environnement assisté par IA ». Source : https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model — VERIFIED
- **c54.** DORA AI Capabilities : sans focus sur l'utilisateur final, l'adoption de l'IA peut peser négativement sur la performance d'équipe. Source : https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model — VERIFIED
- **c55.** Thoughtworks, Radar (novembre 2025) : renforcer les pratiques éprouvées (TDD, analyse statique) et les intégrer aux workflows, par exemple via des instructions partagées pour l'équipe. Source : https://www.thoughtworks.com/radar/techniques/complacency-with-ai-generated-code — VERIFIED
- **c56.** Thoughtworks, billet du 8 juin 2026 : remplacer le contrôle par des « chemins balisés » (plateforme interne approuvée, contrôles automatiques dans le cycle de livraison, priorisation du risque par cas d'usage). Source : https://www.thoughtworks.com/insights/blog/technology-strategy/balancing-innovation-quality-software-governance — VERIFIED
- **c57.** Anthropic (24 juillet 2025, données déclarées par Anthropic) : les équipes les plus efficaces traitent Claude Code comme un « partenaire de réflexion » ; elles confient des problèmes abstraits, laissent l'outil travailler, puis relisent les solutions avant la finalisation. Source : https://claude.com/blog/how-anthropic-teams-use-claude-code — VERIFIED
- **c58.** Anthropic : l'équipe Product Design automatise des commentaires de pull request via GitHub Actions. Exemple d'usage borné, sans mesure publiée. Source : https://claude.com/blog/how-anthropic-teams-use-claude-code — VERIFIED
- **c59.** La revue de code assistée serait un point d'entrée courant des adoptions. Aucune source primaire trouvée pour cette affirmation ; les chiffres d'adoption repérés (c22) ne la démontrent pas. Source : aucune URL retenue — UNVERIFIED

## Ce que ça change pour la formation

- **Ne pas promettre un gain de productivité générique.** Les mesures divergent selon la tâche, la population et l'outil ; le présenter comme une question à mesurer chez le client. Faits : c3, c12, c23 à c28, c29 à c34, c60 à c62.
- **Présenter la revue de code assistée comme un premier passage, mesuré sur le suivi des commentaires.** Faits : c42, c79, c83, c85. Éviter de citer le volume de commentaires ou les benchmarks d'éditeurs comme preuves (c88, c90).
- **Relier perception et mesure.** Faits : c9, c24, c26 à c28. Décider des métriques avant le pilote, comme le recommande GitHub. Faits : c48, c78, c76 à c77.
- **Construire le pilote comme les guides des éditeurs le décrivent.** Petite équipe volontaire, champions, calendrier, sprint d'onboarding. Faits : c45 à c49.
- **Écrire les règles de revue avant d'élargir.** Stance clair, petits lots, pratiques éprouvées, chemins balisés et contrôles automatiques. Faits : c52, c53, c55, c56, c64, c57.
- **Former au débogage et à la compréhension, pas seulement à l'outil.** Faits : c18, c19, c35 à c38, c44.
- **Traiter le shadow AI comme un signal de besoin, pas seulement comme un risque.** Faits : c66, c67, c68, c69.
- **Parler des coûts avec prudence.** Faits : c71 à c74, toutes en presse ou non vérifiées. Ne pas présenter c74 comme établi.
- **Demander au client la liste exacte de ses approbateurs.** Faits : c92 à c99 (sources publiques et cabinets). Le rôle du comité d'architecture et des achats reste à confirmer : c100.
- **Ne pas affirmer ce qui n'est pas sourcé.** c22, c59, c86, c90, c100 sont à exclure des supports tant qu'une source primaire n'est pas retrouvée.
